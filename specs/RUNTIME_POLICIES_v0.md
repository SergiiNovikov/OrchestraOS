RUNTIME_POLICIES_v0.md
1. Статус и область действия

Document: RUNTIME_POLICIES_v0.md
Version: v0
Status: SUBORDINATE TO ARCHITECTURE (non-canonical)
Scope: политики исполнения и runtime-дисциплина поверх архитектуры v0.

Эти политики:

MUST NOT менять архитектуру, роли, границы ответственности или артефакты.

MUST применяться ко всем ролям, определённым в канонических документах архитектуры v0, как единые требования выполнения.

2. Термины и обозначения

MUST

Role Spec — канонический immutable документ роли/класса ролей.

Artifact — выходной объект роли строго по контракту (например *_v0).

Run — один полный прогон пайплайна по одной цепочке ролей (без переиспользования контекста/памяти).

Determinism — свойство, что одинаковые входы и окружение дают идентичные выходы (байт-в-байт, где применимо).

SHOULD

В runtime-логах различать: архитектурные идентификаторы (role_id/spec_id/artifact_type) и исполнительские (run_id, trace_id).

3. Глобальные требования детерминизма

MUST

Determinism > phrasing quality: при конфликте выбирается режим, повышающий повторяемость, даже если формулировка менее “красивая”.

No hidden state: ни одна роль MUST NOT зависеть от диалогового контекста, памяти, кешей “по смыслу”, внешних часов, случайности без фиксации.

Same inputs → same outputs: при неизменных входных артефактах, версиях spec’ов и окружении результат MUST быть идентичен.

Fail-closed: при нарушении контрактов/целостности роль MUST завершаться отказом (см. раздел 6), а не “угадывать”.

SHOULD

При невозможности байт-в-байт идентичности (например, допускается только в конкретных форматах), фиксировать минимальный эквивалентный критерий (например, канонический JSON с сортировкой ключей и нормализацией пробелов) — но только как исполнительское правило сериализации, не меняющее семантику артефакта.

MUST NOT

Автоматически “чинить” входы (trim/normalize/merge) так, чтобы менялась их интерпретация относительно spec’а.

Подмешивать “разумные допущения” для заполнения пропусков.

4. Параметры выполнения моделей

MUST

Для всех LLM-вызовов runtime MUST использовать детерминистический режим:

temperature = 0

top_p = 1 (или эквивалент “не ограничивать вероятностную массу” при t=0)

presence_penalty = 0, frequency_penalty = 0

Если платформа/провайдер поддерживает seed, то:

seed MUST быть задан и MUST быть производным от determinism_key (см. раздел 5) по фиксированному правилу.

Любые параметры, влияющие на текст (например, max_tokens) MUST быть фиксированы политикой и версионированы.

SHOULD

Для каждого role-run логировать полный набор effective-параметров модели (включая модель/версию), чтобы воспроизвести вывод.

MUST NOT

Изменять параметры модели “динамически” на основе содержания входа (например, “если сложно — повысим temperature”).

5. determinism_key и стабильность входов
5.1. determinism_key

MUST

Каждый Run MUST иметь determinism_key, вычисляемый исключительно из:

входного Request Envelope (или эквивалентного первичного входа рантайма),

версий канонических spec’ов (идентификаторы/хэши),

версий runtime policy / implementation guidelines,

фиксированной информации окружения, влияющей на результат (model id/version, tokenizer version, и т.п.).

determinism_key MUST быть стабильным: одинаковые входные данные + те же версии → тот же ключ.

determinism_key MUST быть доступен всем стадиям исполнения как read-only.

SHOULD

Хранить determinism_key в trace-контексте и прикреплять к каждому артефакту как metadata, если это не меняет контракт артефакта (т.е. metadata вне тела артефакта либо в разрешённом spec-ом месте).

MUST NOT

Включать в determinism_key текущее время, случайные значения, сетевые идентификаторы, порядок выполнения потоков, latency.

5.2. Canonicalization входов (исполнительская дисциплина)

MUST

Любая каноникализация, используемая для вычисления determinism_key (например, сортировка ключей JSON), MUST быть:

детерминированной,

документированной в этой политике,

неизменной внутри версии v0.

SHOULD

Использовать канонический JSON (RFC-подобная сериализация): UTF-8, сортировка ключей, нормализация переводов строк.

MUST NOT

Менять пользовательский текст “по смыслу” (например, исправлять опечатки) ради стабильности.

6. Политики отказов и ошибочных состояний (fail-closed)

MUST

Если входной артефакт:

отсутствует,

невалиден по схеме/типу,

не соответствует версии (*_v0) там, где требуется,

содержит противоречивые обязательные поля,
то роль MUST вернуть отказ.

Отказ MUST быть явным, структурированным и машиночитаемым (в рамках допускаемого формата выхода роли/рантайма), и включать:

error_code (фиксированный словарь для v0),

error_class (CONTRACT_VIOLATION / INVALID_INPUT / RUNTIME_FAILURE / UNSUPPORTED_VERSION),

role_id,

artifact_expected,

determinism_key,

minimal diagnostics (без домыслов).

SHOULD

Разделять:

contract-fail (ошибка контракта) — всегда fail-closed,

runtime-fail (инфраструктура) — тоже fail-closed, но с возможностью повторного запуска тем же determinism_key.

MUST NOT

“Проглатывать” ошибки и продолжать пайплайн с частичными/заглушечными результатами.

Подменять отказ “частичным ответом пользователю” внутри ролей.

7. Политики работы с отсутствующими/неполными данными

MUST

Если spec роли требует данные, а их нет, роль MUST:

либо отказать (если данные обязательны),

либо вернуть результат, который явно обозначает отсутствие данных, только если spec допускает “пустой/нулевой” результат.

Любой “empty result” MUST быть отличим от “result with content”.

SHOULD

В тестах иметь отдельные кейсы: missing optional vs missing required.

MUST NOT

Автозаполнять пропуски “правдоподобными” значениями.

8. Версионирование артефактов и совместимость

MUST

Все артефакты MUST иметь версию в имени типа (например, *_v0) и/или в поле версии, если так задано spec’ом.

Рантайм MUST проверять соответствие версии входного артефакта ожидаемой версии spec’а.

Несовпадение версии MUST приводить к отказу UNSUPPORTED_VERSION, если не предусмотрен официальный мост совместимости на уровне рантайма.

SHOULD

При изменении любой политики, влияющей на determinism_key или сериализацию, повышать версию runtime policy (например, v1).

MUST NOT

“Молча” принимать v1 как v0 или наоборот.

9. Логирование и трассировка (без реализации)

MUST

Каждый run MUST иметь run_id и trace_id.

Логи MUST включать:

start/end события для каждой роли,

входные артефакты: идентификаторы/хэши (не обязательно содержимое),

выходные артефакты: идентификаторы/хэши,

determinism_key,

error events (если есть) с error_code.

Логи MUST быть детерминированно упорядочены (по фиксированному порядку ролей и событий), чтобы сравнение прогонов было стабильным.

SHOULD

Разделять уровни: audit-log (минимальный неизменный) и debug-log (расширенный), но оба детерминированы по порядку.

MUST NOT

Писать в логи секреты (ключи API, токены, персональные данные) — если такие вообще проходят через систему, должны быть маскированы на инфраструктурном уровне.

10. Тестирование и контроль соответствия spec’ам

MUST

Spec compliance tests: на каждую роль — тесты валидности входа/выхода по контракту.

Determinism tests: минимум N=3 прогона идентичного входа → идентичный выход (сравнение по канонической сериализации).

Fail-closed tests: набор негативных кейсов должен подтверждать отказ, а не “мягкий” результат.

Golden tests: фиксированные входы → фиксированные эталоны выходов (golden artifacts).

SHOULD

Иметь тест “перестановка порядка нерелевантных полей” (если формат это допускает) → тот же determinism_key и тот же выход.

Иметь тесты на “дрейф окружения” (смена модели/версии) → determinism_key меняется.

MUST NOT

Считать тест пройденным, если выход “примерно похож” (fuzzy match), кроме специально разрешённых форматов, где spec допускает нестрогость.

11. Деплой и воспроизводимость окружения

MUST

Окружение исполнения MUST быть зафиксировано:

версия рантайма,

версия зависимостей,

версия модели/провайдера,

настройки токенизации/сериализации (если применимо).

Любое изменение, влияющее на вывод, MUST отражаться в determinism_key через версию окружения.

SHOULD

Поддерживать режим “replay”: повторить run по сохранённым входным артефактам и determinism_key.

MUST NOT

Выполнять “горячие” изменения параметров модели без изменения версии окружения.

12. Запрещённые приёмы (anti-patterns)

MUST NOT

Heuristic patching: “если не получилось — попробуем иначе”.

Retrying with mutated prompt: повторная попытка с изменённой инструкцией ради “лучше вышло”.

Silent downgrade: принимать неверную версию/схему без ошибки.

Best-effort completion: додумывать пропуски, чтобы “что-то вернуть”.

Non-deterministic ordering: обход коллекций без сортировки, зависимость от порядка словарей/потоков.

Hidden normalization: менять входной текст ради “качества”.
